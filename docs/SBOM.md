# Software Bill of Materials (SBOM)

The remoteagent client ships with an SBOM in CycloneDX format:
[`sbom.cyclonedx.json`](../sbom.cyclonedx.json).

## Runtime dependencies

| Component | Version | Purpose | License |
|---|---|---|---|
| Node.js (runtime) | ≥ 20 | JavaScript runtime | MIT |
| ws | ^8.18 | WebSocket client (optional relay) | MIT |

The client has exactly **one npm dependency** (`ws`) and no transitive
runtime dependencies. Everything else — cloud client, engine, protocol,
tool registry, TUI — is implemented in this repository with Node built-ins.
The client runs directly from source; there is no build step.

## Build & toolchain

| Component | Purpose |
|---|---|
| node:test | Test runner (570 tests at the 2026-08-24 control-plane split, incl. the security red-team suites; no external test deps) |
| npm workspaces | Monorepo layout (`packages/engine`, `packages/protocol`, `apps/desktop`) |

Dev dependencies are none beyond the Node.js test runner.

## Scope and exclusions

The SBOM covers the OSS client only. The enterprise control-plane library
lives in a private server repo and is not part of this client. Release
archives must not contain control-plane code; CI enforces this.

## Regeneration

The dependency tree is what the SBOM reflects, and it is checkable any time:

```bash
npm ls --all --json > /tmp/deps.json   # full tree, dev deps included
npm ls --omit=dev --all --json         # runtime tree: ws only
```

`sbom.cyclonedx.json` is regenerated by the release workflow from the
runtime tree + package metadata. If you hand-edit it, make sure the
component list still matches `npm ls --omit=dev --all`.

For a complete release inventory, run the full `npm ls` dump above and
combine it with the Git tag manifest (`git tag`, `CHANGELOG.md`).

## Server-side (operated by the platform)

The cloud side is a PHP application on standard shared hosting (LiteSpeed,
MySQL/MariaDB, PHP 8.x) plus the Sngine framework for accounts and payments.
Provider SDKs are not used; LLM calls are plain HTTPS REST. Server components
are the operator's responsibility and are documented for audits in this
folder.

## Vulnerability handling

Dependencies are monitored on every change. If a CVE is reported in a
dependency:

1. Triaged within 48 h
2. Fixed / mitigated and released
3. Coordinated disclosure via [SECURITY.md](../SECURITY.md)

Monitoring is `npm audit` on the single dependency per release, GitHub
Security advisories for the repository, and the SECURITY.md reporting path
for external findings.

One dependency means the attack surface stays small — a deliberate
engineering constraint of this project.
